La kata: Tres en Raya

Requisitos y pruebas del enunciado

Requerimiento 1

Una pieza puede estar colocada en un espacio de un tablero 3×3.

  • Fuera del eje X → se lanza una excepción
  • Fuera del eje Y → se lanza una excepción
  • Lugar ya ocupado → se lanza una excepción

Requerimiento 2

Debe existir una forma de determinar qué jugador juega después.

  • El primer turno siempre lo juega 'X'
  • Si el último turno fue 'X', el siguiente es '+'
  • Si el último turno fue '+', el siguiente es 'X'

Requerimiento 3

Un jugador gana si es el primero en conectar una línea de un lado a otro, o de una esquina a otra.

  • Si no se cumple la condición de victoria → no hay ganador
  • Gana con toda una línea horizontal ocupada
  • Gana con toda una línea vertical ocupada
  • Gana con toda una línea diagonal ocupada
Fuente: presentación del curso “3. TDD - CI CD.pdf”, páginas 16 a 18. La implementación TresEnRaya.java (80 líneas) y las dos suites viven en el repositorio local TDD/.

Diferencia 1 · Preparación y estructura

Duplicación vs. setup declarativo

Humano — TresEnRayaTest.java

@Test public void cuandoFueraXlanzarExcepcion() throws Exception{ tresEnRaya = new TresEnRaya(); System.out.println("Inicializando Prueba.... " + ...); exception.expect(Exception.class); tresEnRaya.jugar(5,2); } // este método nunca se ejecuta: public final void before(){ }
  • El objeto se reconstruye dentro de cada prueba (×10), con el mismo println de arranque.
  • before() no tiene @Before: el “arranque” escrito existe pero no corre nunca.
  • Patrón repetido a mano “1. Preparación / 2. Lógica / 3. Verificación” en los 10 métodos.

IA — TresEnRayaIATest.java

private TresEnRaya juego; @Before public void prepararTablero() { juego = new TresEnRaya(); } @Test public void cuandoLaCoordenadaXEsMenorQueUnoSeLanzaExcepcion() { Exception e = assertThrows(Exception.class, () -> juego.jugar(0, 2)); assertEquals("La coordenada 0 esta fuera de lugar", e.getMessage()); }
  • Un solo punto de preparación: si cambia la API del juego, se edita un método.
  • Cero salida a consola: el log de CI muestra solo fallos reales.
  • Nombres largos y descriptivos, en un patrón consistente en los 27 métodos.

Diferencia 2 · Manejo de excepciones

“Falle por la razón correcta”

Humano — cualquier excepción sirve

@Rule public ExpectedException exception = ExpectedException.none(); @Test public void cuandoLugarOcupadoLanzarExcepcion() throws Exception { tresEnRaya = new TresEnRaya(); tresEnRaya.jugar(1,3); exception.expect(Exception.class); // ¡cualquiera! tresEnRaya.jugar(1,3); }
  • ExpectedException está deprecado desde JUnit 4.13.
  • Exception.class acepta cualquier error: un NullPointerException, un fallo de tipeo o una excepción por otra causa dejaría la prueba en verde.
  • Los mensajes no se verifican: 0 de 2.
  • Las coordenadas 0, 4 y negativas nunca se prueban (solo 5).

IA — se valida el contrato público

@Test public void cuandoLaPosicionYaEstaOcupadaSeLanzaExcepcion() throws Exception { juego.jugar(1, 3); Exception e = assertThrows(Exception.class, () -> juego.jugar(1, 3)); assertEquals("La posicion ya esta ocupada", e.getMessage()); }
  • assertThrows devuelve la excepción: se comprueba el mensaje literal del contrato.
  • Una prueba falla si llega una excepción distinta de la esperada.
  • 8 pruebas de coordenadas inválidas (0, 4, 5 y −1 en ambos ejes) + 2 de extremos válidos (1,1) y (3,3).
  • Los 2 mensajes del contrato: 2 de 2 cubiertos.
Riesgo sustancial: con expect(Exception.class) una prueba puede quedar verde por la razón equivocada y ocultar un defecto real; con assertThrows + mensaje, la prueba verifica además que la API se llama exactamente como fue diseñada.

Diferencia 4 · Alcance y proceso

Lo que cada enfoque aporta (y sobrepone)

Humano: intención y proceso TDD

  • Las pruebas nacen antes del código: el historial muestra el ciclo (“hacer fallar intencionalmente”, “corregir el error”, “rompiendo una prueba / error de regresión”).
  • Cada prueba toma una decisión de diseño: define cómo se quiere usar jugar() y siguienteTurno().
  • Sabe qué es relevante para el dominio y no prueba ruido.
  • Límite: se detiene en el mínimo del enunciado: 4 de 8 líneas, sin límites de coordenadas ni mensajes, y con un método de setup que nunca corre.

IA: amplitud y consistencia

  • 27 pruebas en una pasada: casos límite, ambas coordenadas, los 8 tableros ganadores y el empate.
  • Patrón uniforme de nombres, aserciones y comentarios en todo el archivo.
  • Riesgo controlado: tiende a inventar requisitos. Ejemplos que se le pidieron y se descartaron en el prompt 02:
    · “jugar después de un ganador debe lanzar excepción” → no está en el enunciado y la implementación lo permite.
    · “regla propia de empate / contador de turnos” → fuera del requerimiento 3.
  • No vive el ciclo rojo-verde-refactor: entrega todo de golpe, sin la disciplina de paso pequeño.
Lo que comparten: ambas suites se acoplan a los strings exactos de retorno ("X es el ganador", "No hay ganador"), así que un cambio de formato rompe las pruebas; y la propia implementación imprime "Ocupando posicion: x, y" en cada jugada, ruido que convendría eliminar antes del pipeline de CI.

Fortalezas, debilidades y veredicto

Balance de la comparación

Humano · 10 pruebas

Fortalezas

  • Trazabilidad total al ciclo TDD y a la decisión de diseño.
  • Cubre el 100 % de los casos pedidos en la presentación.
  • Código corto, legible y con comentarios de jugada.

Debilidades

  • Setup duplicado + 10 println + before() muerto.
  • Excepciones genéricas: posibles falsos verdes.
  • 4 de 8 líneas ganadoras; sin límites 0/4 ni mensajes.

IA · 27 pruebas

Fortalezas

  • Cobertura 8/8 líneas, ambos jugadores, casos límite y empate.
  • Verifica el contrato (mensajes exactos) con assertThrows.
  • Consistencia, cero ruido en consola, listo para CI.

Debilidades

  • Puede inventar requisitos que nadie definió (filtra el prompt 02).
  • No aporta el proceso TDD: no es “red-green-refactor”.
  • Código más largo (251 líneas) y repetitivo en las secuencias.
Veredicto: la IA no reemplaza las pruebas escritas en TDD; las amplía. El enfoque usado aquí fue: escribir las pruebas con el ciclo rojo-verde-refactor, usar el prompt para generar una segunda suite más exhaustiva, y dejar ambas en verde con mvn -B clean test (42 pruebas, 0 fallos) dentro del pipeline de GitHub Actions.
